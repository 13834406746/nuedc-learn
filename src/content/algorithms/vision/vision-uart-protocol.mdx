## 为什么不能裸发数字

直接把 `err` 的值发过去会出两个问题：

- **粘包**：视觉 50fps 发数据，主控处理不过来时数据会挤在一起，读到的字节错位，一个数字读成两个或乱码。
- **无法校验**：串口偶尔误码（干扰、电平抖动），主控不知道这帧是坏的，拿错误数据控制电机——轻则抖一下，重则冲出赛道。

协议的本质就两件事：**划清帧边界 + 校验完整性**。

## 帧格式设计

一个最小可用协议（5 字节）：

```
0xAA 0x55 | cx(1B) | cy(1B) | checksum(1B)
```

| 字段 | 内容 | 说明 |
|------|------|------|
| 帧头 | `0xAA 0x55` | 双字节帧头，单字节帧头（如 0xAA）在数据里撞车的概率高 |
| cx | 偏差，有符号 | 取 `err & 0xFF`，±127 足够循迹用 |
| cy | 目标纵坐标（可选） | 不需要就发 0 |
| checksum | `(cx + cy) & 0xFF` | 接收方重算比对，防误码 |

再大的数据量（比如传坐标数组、识别结果）就往中间加长度字段，套路一样。电赛视觉数据量小，5 字节帧绰绰有余。

## OpenMV 端发送

```python
def send_frame(uart, cx, cy):
    f = bytearray([0xAA, 0x55, cx & 0xFF, cy & 0xFF, 0x00])
    f[4] = (f[2] + f[3]) & 0xFF
    uart.write(f)
```

配合上一篇的循迹程序，每帧识别后调用 `send_frame(uart, err, b.cy())` 即可。`cx & 0xFF` 处理负数：-30 变成 226，接收方按 int8 读回来还是 -30。

## STM32 端状态机解析

主控端推荐 **IDLE 中断 + DMA + 环形缓冲** 收字节（基础见基础知识板块的《串口接收》），主循环里喂给状态机解析：

```c
typedef enum { S_HEAD1, S_HEAD2, S_CX, S_CY, S_SUM } FrameState;

/* 在主循环里不断从 ringbuf 取字节喂入 */
FrameState st = S_HEAD1;
uint8_t buf[3], idx = 0;
int16_t vision_cx = 0, vision_cy = 0;
uint8_t vision_fresh = 0;

void Vision_ParseByte(uint8_t b)
{
    switch (st) {
    case S_HEAD1: if (b == 0xAA) st = S_HEAD2; break;
    case S_HEAD2: if (b == 0x55) { st = S_CX; idx = 0; }
                  else st = S_HEAD1; break;
    case S_CX: case S_CY: case S_SUM:
        buf[idx++] = b;
        if (idx >= 3) {
            if ((uint8_t)(buf[0] + buf[1]) == buf[2]) {
                vision_cx = (int8_t)buf[0];   /* 有符号偏移 */
                vision_cy = (int8_t)buf[1];
                vision_fresh = 1;
            }
            st = S_HEAD1;
        }
        break;
    }
}
```

状态机设计的要点：

- **状态只在匹配时前进**：帧头不匹配就回 `S_HEAD1` 重新找，这就是「错位自恢复」——哪怕中间丢了字节，下一帧开头也能对齐。
- **校验失败丢弃整帧**：checksum 不对就不更新 `vision_cx/cy`，主控继续用上一帧的合法值，不会用坏数据。
- **`vision_fresh` 标志**：主控用它判断「有没有新数据」。视觉丢帧（比如突然反光找不到目标）时，主控可以基于此做超时处理——N ms 没新帧就停车/保持，而不是用过期值。

## 联调步骤

别上来就连实车调，按四级从简单到复杂：

1. **回环测试**：主控收到什么回发什么（`UART_Send(UART2, b)`），PC 串口助手看能不能原样收回来。这验证硬件链路和波特率。
2. **固定值测试**：OpenMV 端发固定帧（比如 cx=127, cy=0），主控确认稳定解析出 127。
3. **真数据测试**：跑真实识别，串口助手同时监听（逻辑分析仪或双串口），确认发送端和解析端数据一致。
4. **压力测试**：手抖动摄像头、来回移动目标，观察误码率和恢复时间。正常应几乎零误码，且丢帧后 1~2 帧内自恢复。

## 常见坑

- **共地**：视觉模块和主控不共地，串口会随机误码，这是头号杀手。先共地再查别的。
- **电平不匹配**：OpenMV 是 3.3V 逻辑，STM32 板子部分引脚是 5V 容忍。跨电平用同电源共地通常没事，但隔离/转换最稳。
- **波特率容差**：两边晶振误差累积，长帧会错。115200 下 5 字节帧很安全；9600 以下基本不会有问题。
- **时间预算**：一帧 5 字节 @115200 ≈ 0.43ms，相比 20ms 控制周期完全充裕。如果担心，115200 已经比所需快一个数量级。
